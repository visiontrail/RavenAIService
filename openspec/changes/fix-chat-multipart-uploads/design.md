## Context

三个流式入口把全部图片 Base64 JSON 放入普通 `images` 字段。Starlette 默认只允许普通字段 1 MiB，业务层允许的图片容量却更大；前端日志分析异常分支丢弃了 HTTP 错误详情。

## Goals / Non-Goals

**Goals:** 图片走标准文件分段，保留老客户端兼容；沿用管理员配置的图片数量和单图大小；明确区分上传拒绝和连接故障。

**Non-Goals:** 本次不调整 OCR 模型能力、Agent 工作流或客户已有数据。

## Decisions

- 新前端提交重复的 `image_files` 文件字段。服务端使用 `UploadFile` 的临时文件机制，按现有图片限额有界读取并转换为已有 `ImageAttachment`。不使用全局 multipart monkey patch，也不缓冲 SSE。
- `images` 旧字段继续接受。对话路由在 FastAPI 解析前通过公开 `request.form(max_part_size=...)` 设置兼容容量：至少 16 MiB，且足够容纳配置允许的全部 Base64 图片及 1 MiB JSON 余量。不改变文件分段限额及其他路由。
- 图片超限返回 413，包含图片序号、实际大小、限额和处理建议；数量与格式错误返回 400。普通字段解析超限返回可读的 413 和字段限额。提示支持中英文。
- 前端保留 API 的可读详情；代理返回 HTML 413/502/503/504 时使用对应的可操作提示，不向用户显示 HTML。只有未收到 HTTP 响应时显示连接失败。
- 会话工厂首次创建状态时也返回 Vue 响应式代理，保证异步错误直接刷新页面，无需重新选择会话。

## Risks / Trade-offs

- 旧客户端仍有 Base64 内存开销 → 仅对话表单提高有界容量；新客户端采用文件传输，业务校验仍生效。
- 新前端依赖 `image_files` 支持 → 发布时先后端后前端，回退顺序相反。
- 请求在解析阶段失败时不能可靠获知字段名 → 明确提示整段文字/历史/旧版图片字段容量及处理方法，不编造文件名。

## Migration Plan

无需数据库变更。提交代码及回归验证后，另行确认 nr-test 部署范围；保留生产现有改动，只更新授权服务。
