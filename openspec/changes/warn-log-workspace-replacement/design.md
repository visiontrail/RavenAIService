## Context

`LogAnalysisChatService` 对每个 `session_id` 只保存一个当前工作区指针。新日志附件会创建新工作区、更新指针并删除旧工作区；原始日志记录和下载文件独立保留。`AIChat.vue` 当前允许同一会话继续选择文件并发送，却没有在不可逆的工作区替换前告知用户。前端运行态已经由 `conversationRuns` store 按 session 隔离，并能接收仅在附件上传成功后发出的 `log_analysis_context` SSE 事件。

## Goals / Non-Goals

**Goals:**

- 在同一 session 的第二次及后续日志附件上传真正发出前明确告知工作区替换语义。
- 给用户三条无歧义路径：继续并替换；新建对话独立分析；在新对话同一轮上传全部相关日志做关联分析。
- 确保首次上传、纯文字追问、图片附件和其他 Agent 不触发提示。
- 状态按 session 隔离，并在历史会话重新加载后仍能识别已有日志附件上下文。

**Non-Goals:**

- 不改变后端“一 session 一个当前工作区”的清理策略。
- 不永久保留历史 Agent 工作区，也不实现历史工作区切换。
- 不改变日志列表、原始日志下载或多附件同轮分析能力。

## Decisions

### 1. 在发送边界确认，而不是选择文件时立即弹窗

用户可能连续选择多份文件组成同一轮附件集合，因此确认放在 `sendMessage()` 确定本轮会走日志分析、且即将发请求时执行。这样文件选择/拖拽过程不中断，并保证取消或关闭提示时不会创建 run、清空输入或清空附件。

选择文件时立即提示的替代方案会在多选和拖拽补充附件时重复打断用户，故不采用。

### 2. 在 session-scoped run store 记录既有日志工作区事实

`ConversationState` 增加布尔状态。日志上传成功后端发出 `log_analysis_context` 时置为真；加载持久化历史时，通过后端已经写入用户消息的稳定 `[日志附件]` 标记恢复。新建 session 的默认值为假，切换会话天然隔离。

只使用 `chatHistory.length > 0` 或 `lastAgentKind == log_analysis` 会误判纯文字追问、失败运行及从 GeneralAgent 路由到日志分析的消息，因此不采用。

### 3. 提供“继续并替换”“新建对话”和关闭三种结果

Element Plus 确认框把更安全的“新建对话”设为主按钮；次按钮继续当前发送并替换工作区；关闭按钮不执行任何动作。新建对话会保留用户刚选择的待发送附件与项目选择。提示正文明确：

- 继续会让 AI 后续无法读取此前上传的日志；
- 原日志的列表记录和下载不受影响；
- 独立分析使用新对话；
- 关联分析必须在新对话的同一轮上传全部相关日志。

新建对话后不自动发送，避免用户尚未补齐关联分析所需的旧附件时误发请求。

### 4. 将判断与确认结果归一化提取为纯函数

把触发条件、历史附件标记识别和确认动作归一化放入可独立测试的前端工具模块。`AIChat.vue` 只负责展示对话框和执行“继续/新对话/关闭”结果，减少组件内难以在 Node Vitest 环境验证的分支。

## Risks / Trade-offs

- [历史附件识别依赖 `[日志附件]` 文本标记] → 同时以实时 `log_analysis_context` 为主路径；为持久化历史标记识别写回归测试，并将识别集中在单一工具函数中。
- [用户点击新建对话后误以为已经开始分析] → 保留附件但不自动发送，让用户可以补齐关联日志并检查项目选择。
- [多标签页可能在本地状态上不一致] → 提示属于客户端保护；后端仍保留运行中拒绝和工作区替换规则作为最终约束。
- [提示增加一次操作] → 仅对会覆盖既有日志上下文的上传触发，首次上传和无附件追问不增加摩擦。
