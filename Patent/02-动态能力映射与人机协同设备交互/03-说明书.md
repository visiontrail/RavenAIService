# 说明书

**发明名称：一种基于动态能力映射与人机协同权限管控的AI智能体远程设备交互方法、系统、电子设备及存储介质**

---

## 一、技术领域

本发明涉及人工智能与物联网技术领域，尤其涉及一种基于动态能力映射与人机协同权限管控的AI智能体远程设备交互方法、系统、电子设备及计算机可读存储介质，可应用于智能运维平台、工业物联网管控系统、智能家居中枢、边缘设备管理平台等以大语言模型智能体为交互入口、通过网络远程操控异构设备的场景。

## 二、背景技术

随着大语言模型（Large Language Model，LLM）与智能体（Agent）技术的发展，越来越多的场景尝试将大语言模型智能体作为用户与物联网设备、边缘计算节点等远程设备之间的自然语言交互中枢：用户以自然语言描述意图，智能体将意图转化为设备工具调用并将执行结果汇总后以自然语言反馈给用户。

然而，现有技术在将大语言模型智能体与远程设备对接时存在如下缺陷：

（1）**静态工具配置问题**：现有方案通常在服务端硬编码支持的设备工具列表，每当新增设备型号或设备固件升级新增工具后，需要修改服务端代码并重新部署。在异构设备种类多、固件迭代频繁的场景下，维护成本极高且无法做到实时适配。

（2）**无差别工具权限问题**：现有方案对大语言模型发起的工具调用不区分操作风险等级，或仅做粗粒度的全局允许/拒绝控制。这导致智能体可能在未经用户确认的情况下执行具有破坏性的设备操作（如恢复出厂设置、固件刷写、关键参数修改），造成不可逆损害；或者为求安全而全局阻断，丧失了自动化的价值。

（3）**设备应答不可信问题**：远程设备返回的工具执行结果可能包含超大负载（导致上下文窗口溢出）、不符合预期模式的畸形数据（导致模型产生幻觉式解读）、或嵌入了认证令牌等敏感凭证（经模型引用后泄露至用户界面）。现有方案通常将设备应答原样回喂模型，缺乏系统化的结果审查与净化机制。

（4）**协议版本碎片化问题**：设备固件版本不一，新设备支持结构化协议而旧设备仅支持文本协议。现有方案要么仅支持单一协议版本，要么在每个设备适配层单独编写版本兼容代码，架构重复且容易遗漏。

（5）**指令歧义盲执行问题**：用户的自然语言指令往往存在歧义（缺少必要参数、目标设备不明确、操作范围模糊），现有方案中智能体通常基于猜测执行，或在对话中以自由文本追问，缺乏结构化的、带预设选项的澄清机制来降低用户输入成本与误操作风险。

综上，现有技术缺乏一种能够同时解决**设备能力动态适配、工具调用分级权限管控、设备应答系统化审查、协议版本透明适配与结构化指令澄清**的完整技术方案。

## 三、发明内容

### （一）要解决的技术问题

本发明所要解决的技术问题包括：

1. 异构设备能力动态变化，服务端工具集无法实时适配的问题；
2. 大语言模型智能体对远程设备工具调用缺乏分级权限管控，存在未经用户确认执行破坏性操作的安全风险；
3. 远程设备返回的工具执行结果可能包含超大负载、畸形数据或敏感凭证，直接回喂模型导致的上下文溢出、幻觉及信息泄露风险；
4. 不同固件版本的设备使用不同通信协议，需要透明适配的问题；
5. 用户自然语言指令存在歧义时，缺乏结构化澄清机制导致的误操作问题。

### （二）技术方案

为解决上述技术问题，本发明提供一种基于动态能力映射与人机协同权限管控的AI智能体远程设备交互方法，其总体构思为：**在设备接入维度建立"能力声明→进程内代理工具"的动态映射机制，在工具调用维度建立"三级风险归类→人机协同审批→后置结果校验"的全链路安全管控机制，在通信维度建立协议版本自适应分发机制，在交互维度建立基于结构化选项的主动澄清提问机制**。

方法主要步骤如下：

**步骤 S1，设备能力接收与状态管理。** 服务端通过长连接通道（本实施例中为 WebSocket）接收远程设备的注册消息与能力声明。设备信息（标识、名称、主机地址、可用模型列表、能力字典、状态、最近心跳时间）被记录到设备状态表中。设备连接管理模块支持心跳监测、断线标记、能力热更新与状态持久化（序列化至磁盘文件，服务重启后恢复为离线状态）。

**步骤 S2，动态能力→工具映射。** 每次智能体会话开始时，从设备能力声明中提取工具服务描述列表，对每个工具服务描述执行如下处理：

1. **名称净化**：将服务名称与工具名称中的非法字符替换为下划线，去除首尾下划线，按 `mcp__device__<服务名>__<工具名>` 格式生成代理工具名称；
2. **参数模式归一化**：优先读取 `inputSchema`，回退读取 `input_schema`，均缺失时生成开放式对象模式；`outputSchema` 以同样方式可选读取；
3. **风险等级归一化**：读取 `risk` 或 `x-risk` 字段，将别名（`readonly`/`safe`/`ro`→只读，`mutating`/`rw`→写入，`danger`/`dangerous`/`irreversible`→破坏性）归一为三级标准值；
4. **工具元数据生成**：创建包含代理工具名称、原始服务名/工具名、描述、输入模式、输出模式与风险等级的工具元数据记录；
5. **代理工具函数生成**：通过闭包工厂为每个工具服务描述生成异步代理函数，函数在被调用时将参数打包、生成唯一请求标识、调用分发器转发至设备、包装返回结果；
6. **工具数量上限截断**：当工具总数超过预设上限（本实施例默认 64 个）时，按 (服务名, 工具名) 排序后仅保留前 N 个，截断的工具名称通过事件推送通道通知。

所有代理工具函数注册到一个进程内工具服务器对象，连同允许工具名称列表与工具元数据映射表一并返回给调用方。

分发器将请求信封封装为长连接通道的消息帧（`PromptEnvelope`），其元数据段携带来源标识、协议版本、原始服务名与工具名以便上下游链路追踪。

**步骤 S6，后置校验。** 推理引擎对设备代理工具的每次调用结果均经过后置校验钩子处理。钩子通过通配模式匹配器仅拦截以设备代理工具前缀（`mcp__device__*`）开头的工具名称，对内置工具与其他来源工具不做拦截。校验流程如下：

1. **信封解析**：从推理引擎传递的工具响应对象中提取 `content[0].text` 并解析为结构化字典；解析失败时构造模式不匹配错误占位；
2. **总长度校验**：原始信封超过预设字节上限时直接替换为结果过大错误对象；
3. **错误类型归一化**：设备返回的 `error_kind` 字段若不在已知错误类型集合中则归一为内部错误，已知错误直接透传（不当作校验失败）；
4. **输出参数模式校验**（轻量级）：仅校验顶层数据类型与必需字段存在性，不引入外部模式校验依赖；不合格时替换为模式不匹配错误对象并附截断后的原始内容摘要；
5. **证据条目截断**：`evidence` 列表中每条文本超过预设摘要字节上限时截断并标记 `truncated=true`；截断点按 UTF-8 多字节字符边界安全回退；
6. **凭证脱敏**：对所有文本字段（错误消息、证据、结果体）应用 `mask_tokens` 正则替换嵌入式认证令牌；对工具调用参数应用 `mask_input` 递归脱敏；
7. **二次大小校验**：脱敏后的最终负载再次校验总长度；
8. **结果替换**：将处理后的结构化字典序列化为 JSON 文本，封装回推理引擎期望的工具输出格式（`{"content":[{"type":"text","text":"..."}]}`），通过钩子返回值的 `updatedMCPToolOutput` 字段替换原始输出。

**步骤 S7，主动澄清提问。** 服务端可选地向推理引擎注册 `AskUserQuestion` 澄清工具（由用户偏好配置控制是否注册）。该工具接受包含一个或多个结构化问题的参数，每个问题含标题（≤12 字，用于界面标签展示）、完整问题文本、可选的多选标志、以及 2~4 个预设选项（每个选项含标签与描述）。

澄清工具与权限管控共享同一权限代理器：调用时在代理器中创建澄清类型的异步等待对象，发出 `clarification_request` 事件，阻塞推理循环等待用户作答。用户通过预设接口提交答案（每个问题可选择预设标签和/或输入自由文本），答案被格式化为人类可读的结构化文本块回喂模型继续推理。

### （三）有益效果

与现有技术相比，本发明具有如下有益效果：

1. **设备能力实时适配**：工具集在每次会话开始时从设备能力声明动态生成，无需服务端代码修改与重部署；设备能力热更新后下次会话即可感知新增或变更的工具，极大降低了异构设备的接入与维护成本；
2. **分级安全管控**：三级风险归类结合只读自动放行、写入/破坏性人工审批的策略，在不牺牲只读操作自动化效率的前提下，从根源上阻止了未经用户确认的高风险操作；默认写入的兜底策略确保任何未知工具均需人工确认，宁严勿漏；
3. **设备应答可信度提升**：后置校验钩子系统化地拦截超大负载、畸形数据与嵌入式凭证，防止上下文窗口溢出、模型幻觉与敏感信息泄露；轻量级输出模式校验在不引入外部依赖的前提下保障了结果结构的基本正确性；
4. **协议透明适配**：协议版本自适应分发使同一服务端代码同时支持新旧版本设备，版本差异对大语言模型推理引擎完全透明，消除了逐设备编写版本兼容代码的架构重复；
5. **误操作率降低**：结构化澄清提问机制使智能体在指令歧义时以预设选项的方式主动询问用户，相比自由文本追问降低了用户输入成本与理解偏差，减少了因歧义导致的误操作；
6. **审批与澄清基础设施复用**：权限审批与澄清提问共享同一权限代理器与异步等待基础设施，降低了系统复杂度与维护成本，且以全局唯一的请求标识保证两类请求互不串扰；
7. **设备状态跨重启保持**：设备信息持久化至磁盘使服务重启后已知设备列表保留（初始为离线），避免了重启后设备清单丢失需要设备全部重新注册的问题；
8. **设备断线即时感知**：设备断线时遍历并以异常完成所有以该设备为目标的待处理异步等待对象，使调用方在毫秒级感知设备不可用，避免长时间无效等待。

## 五、具体实施方式

为使本发明的目的、技术方案和优点更加清楚，以下结合附图与实施例对本发明作进一步详细说明。应当理解，此处所描述的具体实施例仅用于解释本发明，并不用于限定本发明。在不冲突的情况下，下述各实施例及实施例中的特征可以相互组合。

### 实施例一：系统总体架构

如图 1 所示，本实施例的AI智能体远程设备交互系统部署于服务端，包括设备连接管理模块、动态工具映射模块、风险归类模块、权限代理模块、后置校验模块与协议适配模块。系统通过 WebSocket 长连接与远程设备通信，通过 SSE（Server-Sent Events）向用户端推送事件。

### 实施例二：动态能力→工具映射

如图 2 所示，每次智能体会话开始时，动态工具映射模块执行如下步骤：

1. 从设备状态表中获取目标设备的 `DeviceInfo` 对象，提取 `capabilities.mcp.servers[]` 列表；
2. 展开所有服务的工具列表为 `(服务名, 工具名, 原始条目)` 三元组列表，按 (服务名, 工具名) 排序以保证确定性；
3. 对总数超过上限的部分截断并生成通知事件；
4. 对每个三元组：执行名称净化、参数模式归一化、风险等级归一化，创建 `ToolMeta` 元数据记录，并通过闭包工厂生成代理工具函数；
5. 将所有代理工具函数注册到进程内工具服务器对象（本实施例中使用 `create_sdk_mcp_server`），返回 `(server, allowed_tool_names, tool_meta_map)` 三元组。

名称净化的正则规则为 `[^A-Za-z0-9_]+` → `_`，去除首尾下划线，空结果以 `unknown` 替代。代理工具名称格式为 `mcp__device__<净化服务名>__<净化工具名>`。

代理工具函数的闭包上下文包含：原始服务名/工具名、分发器引用、会话标识、目标设备标识、协议版本、事件发射器引用、共享状态字典（用于降级通知去重）与序列号计数器。函数被调用时：将参数规范化为字典、生成 UUID 请求标识、调用分发器、异常兜底为错误结构体、将返回值包装为推理引擎期望的 `{"content":[{"type":"text","text":"..."}]}` 格式。

### 实施例三：三级风险归类与人机协同权限管控

如图 3 所示，推理引擎发起工具调用时，系统执行如下步骤：

1. 从工具元数据映射表中查找当前工具的 `ToolMeta`，调用 `classify_risk` 按三级优先级确定风险等级；
2. 若风险为只读，直接返回 `{"behavior":"allow"}` 短路放行；
3. 若风险为写入或破坏性，生成 UUID 请求标识，构造审批理由文本（`[风险等级] 服务名.工具名: 描述`），对调用参数执行 `mask_input` 递归脱敏，通过事件发射器推送 `tool_permission_request` 事件；
4. 在权限代理器中以请求标识创建异步等待对象（`asyncio.Future`）；
5. 以配置的超时时长 `await asyncio.wait_for(future, timeout)` 等待用户裁决；
6. 超时时自动调用 `broker.cancel(request_id, reason="timeout")`，推送 `tool_permission_resolved` 事件并返回 `{"behavior":"deny","message":"permission timeout"}`；
7. 用户裁决到达时解析 `decision` 字段：`allow` 时返回允许（若携带修正参数则附带 `updatedInput`）；其它一律按拒绝处理。

### 实施例四：单次设备工具调用全流程

如图 4 的时序所示，一次完整的设备工具调用流程为：

1. 推理引擎在推理过程中决定调用某设备工具，触发 `can_use_tool` 回调；
2. 风险归类器确定风险等级；只读直接放行，否则通过权限代理器发起审批；
3. 用户在前端审批界面做出裁决，通过 HTTP 接口写回权限代理器；
4. 权限代理器恢复推理循环，推理引擎调用代理工具函数；
5. 代理工具函数通过分发器将调用封装为请求信封，按协议版本选择格式；
6. 请求信封通过 WebSocket 发送至设备，设备执行工具并返回 `prompt_result`；
7. 设备连接管理模块解析 `prompt_result`，以请求标识匹配待处理映射表中的异步等待对象并写入结果；
8. 代理工具函数接收结果，包装为推理引擎格式；
9. 后置校验钩子拦截输出，执行信封解析、模式校验、截断与脱敏，替换输出；
10. 处理后的结果回喂推理引擎继续推理。

### 实施例五：后置校验钩子

如图 5 所示，后置校验钩子的构造与执行流程如下：

通过 `HookMatcher(matcher="mcp__device__*", hooks=[validator])` 创建仅匹配设备代理工具的钩子匹配器，非设备工具不被拦截。

`validator` 异步函数从 `input_data` 中提取 `tool_name` 与 `tool_response`，依次执行：

1. **信封解析**（`_extract_envelope`）：从 `tool_response.content[0].text` 解析 JSON；失败时构造 `schema_mismatch` 占位；
2. **规范化处理**（`_normalize_envelope`）：
   - 总长度校验：超过 `max_bytes`（本实施例默认 256KB）直接替换为 `result_too_large` 错误；
   - 设备侧错误透传：`status=error` 或存在 `error_kind` 时，仅做脱敏与证据截断后原样透传；
   - 输出模式校验：从工具元数据取 `outputSchema`，校验顶层类型与必需字段；不合格替换为 `schema_mismatch`；
   - 正常结果：脱敏 `result`，截断 `evidence` 中单条超过 `excerpt_bytes`（本实施例默认 16KB）的条目；
   - 二次大小校验：脱敏后重新校验总长度；
3. **结果替换**：序列化处理后的结构体，封装为 `updatedMCPToolOutput` 返回。

每次校验后发出 `result_validation` 事件，记录校验状态（`ok`/`schema_mismatch`/`truncated`/`error`）与失败原因。

UTF-8 安全截断算法：定位到 `max_bytes` 位置后向前回退，跳过所有 `(byte & 0xC0) == 0x80` 的续字节，确保不截断在多字节字符中间。

### 实施例六：协议版本自适应分发

如图 6 所示，分发器的协议适配逻辑如下：

1. 从设备 `capabilities.protocol_version` 读取协议版本，对非整数值（包括布尔值、非数字字符串）容错为 0；
2. `protocol_version >= 2`（结构化协议）：构造 JSON 信封 `{"protocol_version":2,"action":"mcp_call","server":"...","tool":"...","args":{...},"request_id":"...","permission_decision":"allow","ts":"..."}`；
3. `protocol_version < 2`（文本协议）：构造以 `【DEVICE_TASK】` / `【/DEVICE_TASK】` 定界的结构化文本信封，含目标声明、工具选择、参数 JSON、执行约束与期望返回格式；
4. 文本协议首次使用时通过共享状态字典中的标记（`_legacy_envelope_sent`）检测，仅发送一次 `system_notice` 降级通知事件，避免重复通知；
5. 无论何种协议版本，请求信封均封装为 `PromptEnvelope` 对象，元数据中记录实际使用的协议版本、来源标识与原始服务名/工具名。

设备返回的 `prompt_result` 通过 `_parse_device_reply` 统一解析：已是结构化 JSON 直接使用；`answer` 字段为 JSON 字符串则解析后使用；均不满足时包装为 `{"status":"ok","result":{"answer":"..."}}`。

### 实施例七：主动澄清提问

如图 7 所示，澄清工具的注册与执行流程如下：

1. 会话开始时，若用户偏好 `clarification_enabled=true`，构建澄清工具的进程内工具服务器并注入推理引擎的工具集合；
2. 推理过程中模型判断指令歧义时调用 `AskUserQuestion`，传入结构化问题列表；
3. 工具函数首先规范化问题列表（丢弃无效条目），然后检查当前运行已提问次数是否超限；
4. 未超限时生成 UUID 请求标识，在共享权限代理器中创建澄清类型的异步等待对象，发出 `clarification_request` 事件（携带问题列表、运行标识与会话标识）；
5. 用户通过 HTTP 接口 `POST /chat/clarifications/{request_id}/resolve` 提交答案（每个问题支持选择预设标签和/或输入自由文本）；
6. 代理器将答案写回异步等待对象，工具函数恢复并将答案格式化为人类可读文本块回喂模型；
7. 超时时：`on_timeout=continue` 返回提示模型自行推断的文本；`on_timeout=cancel` 调用取消回调终止本轮运行。

### 实施方式总结

需要说明的是：本发明各实施例中的"大语言模型推理引擎"可为任意支持工具调用的大语言模型服务或智能体运行时；"长连接通道"可为 WebSocket、gRPC 流或其他双向长连接协议；"事件推送通道"可为 SSE、WebSocket 推送或其他异步通知机制；存储介质可为磁盘文件系统、对象存储或数据库等价物；上述实施例中的字段名、阈值、协议版本号均为示例。凡在本发明的精神和原则之内所作的任何修改、等同替换和改进等，均应包含在本发明的保护范围之内。
